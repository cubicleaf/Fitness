- 2026-09-21: The stored Groq model id is validated against the offered list, not merely against being absent. What: `getStoredGroqModel` read `localStorage.getItem(GROQ_MODEL_STORAGE) || FITLOGS_AI_MODELS[0].id`, so the default only rescued a *missing* key — a key present but holding a retired id was returned and sent to Groq unchanged. It now checks membership in `FITLOGS_AI_MODELS` and falls back otherwise. Why: Groq retires models on its own cadence (three deprecations across Jun–Aug 2026), so the day an id changes in that array, every browser that had already picked the old one would keep sending a dead name indefinitely. The failure was also mis-presented: with a stale id neither model pill matches, so none highlights, and the helper line falls back to describing `FITLOGS_AI_MODELS[0]` while a different model is actually in use. How to apply: both live ids (`openai/gpt-oss-120b`, `qwen/qwen3.6-27b`) were confirmed current on 2026-09-14 and are the models Groq itself names as replacements for the deprecated Llama tier — this app has never pointed at Llama. Verified by table: a valid id passes through, `null`/retired/garbage all fall back to the default.

- 2026-09-07: Activity retrieval was hiding activities that exist. Three surfaces, one disease. What: (1) the **Add Activity picker** hard-filtered its default list to the current split, so on a push day it showed 7 of 34 activities and anything with no split, a different split, or different capitalisation was simply absent until you searched — the filter is now a **priority sort**, with the split's activities under a heading and the rest under "Everything else". (3) See the search decision below. Why: INTENT says "Suggestions, not mandates. Named splits are labels, not locked lists" — the picker was treating them as locked lists, and STATUS has flagged retrieval trust as the real risk in this area since July. How to apply: no discovery surface may remove an activity from reach. Narrowing is the search box's job; a split is a sort key.

- 2026-09-07: The search scorer could not match a partial word, a typo, or gym shorthand — and a zero-result search invited creating a duplicate. What: `activitySearchScore` previously only matched a whole-string containment or an exact token-set equality, so `dumb should`, `skulcrusher`, `bb row`, `rdl`, `cable rw` and `leg crul` all returned **zero**, at which point the empty state said "Create a new activity above" and the create form's duplicate checker was the thing that finally surfaced the existing activity. Added, all ranked *below* the existing exact tiers so ordering does not regress: per-token prefix matching (800), whole-compact-name fuzzy match (810), Damerau-Levenshtein typo tolerance with a length-scaled budget (650/420), a small gym-abbreviation table — db, bb, ohp, rdl, kb, bw (780/480), and fzf-style subsequence matching as the lowest signal (380/250). Why: false negatives here are far more expensive than false positives — an extra row costs a glance, a missed match costs a duplicate activity and a split history. How to apply: `boundedEditDistance` bails as soon as the answer cannot be within budget, so non-matches stay cheap; keep new tiers below 825 so exact matches always win. Verified 18/18 real-data queries plus exact-match ranking and no false positives on nonsense.
